Computer vision meets physiological sensing

OpenVitals

Ongoing product · Wellness & researchProduct direction, SDK architecture, and AI-assisted engineering

What if the next sensing interface was already in your camera?

OpenVitals transforms subtle changes in facial colour into pulse signals that applications can use. It combines classical signal processing, native performance, and local model inference in an SDK spanning iOS, Android, macOS, Windows, and Linux.

Everyday hardware. Local processing. One shared engine.

01 /A different way to see a camera.

A camera usually captures what a person looks like. OpenVitals explores a more powerful possibility: using the same stream of pixels to reveal the tiny colour changes associated with blood flow beneath the skin.

Those changes are too subtle to judge by eye. The SDK extracts them from facial regions, reconstructs a pulse waveform, evaluates its quality, and returns structured estimates to the host application. This technique is called remote photoplethysmography, or rPPG.

The idea is a shift from a specialised sensing interaction to a software capability built around familiar hardware. The camera-pulse path uses an ordinary camera; the SDK makes that signal accessible to application developers through a consistent interface.

OpenVitals brings this idea beyond a single demo. Its portable C++ core connects to Swift, Kotlin, and Python, alongside direct C and C++ integrations. Around that core sit dedicated research assessment paths, local model runtimes, and tools for recording and comparing scalar results.

Capture locally, process locally, and integrate physiological insight into the application’s own experience.

Existing hardware, a new purpose

OpenVitals looks for a physiological signal inside camera frames already available to an application. The opportunity is to extend the usefulness of laptops and phones through software, bringing contactless pulse sensing into familiar interfaces.

Reusable across applications

A shared native engine provides the processing foundation across five platform targets. Developers integrate through the language and packaging conventions of their application: Swift Package Manager for Apple platforms, Kotlin and JNI for Android, CMake for native desktop applications, and Python for analysis and evaluation.

Processing stays close to the person

The sensing engine and model inference run locally. The core processes frames in memory without recording or uploading them. Host applications control camera permissions and presentation; research exports are deliberate actions. This architecture supports private, responsive experiences without making cloud inference part of the sensing loop.

Signal quality is part of the product

A number is useful only when its source is understood. OpenVitals carries readiness, source timing, and quality information alongside its estimates. Applications can distinguish warm-up, motion, missing faces, irregular sampling, and usable signal states instead of treating every frame as a measurement.

Capture, signal processing, research assessments, and presentation have distinct responsibilities. The camera-pulse pipeline and dedicated research paths retain their own spatial and temporal input requirements, then return a consistent structured result.

04 /The engineering behind the signal.

Building an engine instead of a one-off camera demo

The architectural challenge was to make camera sensing reusable across very different application environments. OpenVitals separates capture, signal processing, research assessments, and presentation. Applications retain control of their camera and UI, while the native core accepts explicit pixel layouts, row strides, face geometry, and monotonic timestamps.

A C++17 core exposed through a versioned C ABI provides a common integration boundary. Swift and Kotlin wrappers manage application-facing types and engine lifetime. Python adds an independent processing pipeline, a native bridge, command-line tools, and repeatable offline evaluation.

Making time part of the signal

Camera frame rates are not perfectly regular. A stream requested at 30 frames per second can arrive at a different cadence, and processing pressure can introduce gaps. OpenVitals uses observed timestamps, bounded interpolation, and source-density checks so the processing grid stays connected to real camera observations.

Each output uses its own analysis window. This keeps a longer breathing or variability calculation from changing how the heart-rate signal is conditioned. Source timing and freshness remain attached to derived results as they move through the assessment pipeline.

Finding a tiny signal inside a moving image

Pulse-related colour variation shares the image with much stronger effects from motion, exposure, lighting, and facial-region selection. The pipeline combines region sampling, colour projections, filtering, spectral analysis, and harmonic checks to identify candidate pulse rhythms.

The investigation also exposed how acquisition choices affect output: preserving camera timestamps, managing browser backpressure, and comparing wider skin regions helped move Mac webcam testing from missing readings to recurring live pulse estimates. Deterministic replay and synthetic positive and negative controls made these changes inspectable and repeatable.

Designing the evidence alongside the SDK

OpenVitals includes tools for exploring where an estimate came from. Shared scalar records carry units, readiness, source times, and provenance across language boundaries. An offline review flow supports importing reference data and comparing aligned observations.

The repository also includes automated checks for numerical behaviour, C ABI contracts, lifecycle handling, concurrency, model execution, and memory safety. This makes the evaluation workflow part of the engineering product rather than an afterthought.

05 /A wider research framework.

Camera-pulse estimates, dedicated model-based research assessments, and derived indicators serve different purposes. Their inputs and interpretation stay distinct within the SDK.

A framework for 12 assessment categories
Heart rate
Quality-gated camera-pulse estimation.
Respiratory rate
Experimental breathing-rate estimation from pulse-amplitude modulation.
Heart rate variability
Analysis of accepted pulse intervals, with duration-aware time and frequency metrics.
Stress index
An experimental pulse-interval histogram index.
Blood pressure
Dedicated two-region signal preprocessing and pretrained research model inference.
Oxygen saturation
A dedicated optical research assessment using nose-region colour signals.
AFib pattern
A research classifier for pulse-pattern assessment.
Cardiovascular age
A derived indicator using variability and normative-table lookups.
Cardiovascular BMI
A derived model-specific indicator, separate from physical BMI.
Cardiovascular risk
A model-based research assessment using explicit, complete source inputs.
Pulse respiration quotient
The relationship between available heart-rate and respiratory-rate estimates.
Wellness indicators
Six configured research mappings for activity, sleep, equilibrium, metabolism, health, and relaxation.

These categories have distinct input contracts. They represent assessment breadth, rather than twelve direct measurements from one camera waveform. Some derived scores also require profile data or external inputs.

06 /Connecting the product and the engineering.

I lead OpenVitals’ product direction, architecture, and AI-assisted engineering, connecting the signal-processing engine, native platform integrations, research workflows, and evaluation tools into a coherent SDK. The work combines systems engineering with practical camera investigation: turning an interesting sensing technique into a foundation other developers can integrate.

The SDK integrates third-party pretrained models. The OpenVitals source and bundled weights have separate ownership and terms.
